## N+1 Diagnosis Results  
BEFORE
- Query count: 1
- Rows transferred: 300 rows × 8 columns = all data
- Filtering: in C# memory (after get from DB)
- SQL: SELECT * FROM VitalSigns (no WHERE, no TOP)

### Endpoint 1: GET /api/v1/VitalSigns/critical

**Observed behavior (with query logging):**
- 1 query: `SELECT * FROM VitalSigns` — loads all 300 rows into memory
- 0 additional queries (no N+1 technically)
- **But:** pulls all 300 rows across the network when only ~5-10 are Critical

**Root cause:** `GetAllAsync()` returns `IReadOnlyList<T>` — all filtering happens in C# memory, not SQL. With 300 records it's wasteful; with 300,000 it's a production outage.

**Category:** Full Table Load (worse than N+1 at scale)
**Sprint 3 fix:** Rewrite using `IQueryable<T>` + `.Where()` + `.GroupBy()` pushed to SQL

---

### Endpoint 2: GET /api/v1/VitalSigns (Doctor)

**Observed behavior:**
- 1 query: `SELECT * FROM VitalSigns`
- Response has no patient name — frontend would need to call GET /Patients/{id} per row

**Category:** Missing projection — data returned is incomplete for real use, forcing client-side N+1
**Sprint 3 fix:** Add projection with patient name included directly

---

### Endpoint 3: GET /api/v1/Patients (with filters)

**Observed behavior:**
- 1 query with WHERE/ORDER BY/OFFSET-FETCH — this one is already clean ✅
- No N+1, no full table load

**Category:** No fix needed — existing `IQueryable<T>` approach is correct

## Key Takeaway
The most dangerous performance bug found today is not N+1 — it is the pattern of calling `GetAllAsync()` and filtering in memory. With 2 patients in development it is invisible. With 20 patients and 300 readings it starts to feel slow. With real hospital data (thousands of patients, millions of readings) it would bring the server down. The fix is to never load what you do not need — push every filter, sort, and aggregation to the database.
